# Standalone balance onboarding spike

Direct Arkade OS SDK 0.4.71 Signet experiment. No imports from BIS integration, no production wallet state, and no backend beyond Vite.

From the repository root with its existing dependencies installed:

```powershell
npm run dev --workspace @spike/balance-onboard
npm run build --workspace @spike/balance-onboard
npm run test --workspace @spike/balance-onboard
```

Open http://127.0.0.1:5186/spike1/ for the standalone server, or http://127.0.0.1:5174/spike1/ when the local integration demo is running. The URL includes a window ID and, once the account is ready, its actual public `btcAddress`. Each origin keeps separate browser storage; an existing account on port 5186 stays there. These local Windows servers require no SSH tunnel.

The six steps identify ownership and approximate duration: CPU Create account; USER Open faucet and fund; CPU Wait for incoming Bitcoin; CPU Onboard selected percentage; CPU Track Bitcoin to Arkade; CPU Confirm usable Arkade funds. Create is explicit on a fresh origin. **Seed Phrase Creation** selects **Auto** (default) or **Manual**. The single **Restart** button generates a phrase in Auto mode or prompts locally for a valid English BIP39 phrase in Manual mode. Restart remains enabled and asks for confirmation. Confirming archives the previous encrypted account and operation, including unresolved transfers, then reloads with the generated or entered identity. It does not cancel submitted transfers or move funds from the previous account. Cancel leaves the current run unchanged.

Copy the public address and click **Open faucet and fund** to open [signet.2nd.dev](https://signet.2nd.dev/). Incoming transaction evidence appears in Step 3 automatically. Step 4 automatically onboards the percentage selected in Step 1 after fresh network checks confirm eligible funding. It freezes the funded input set under the operation lock before submitting; later refreshes cannot start a duplicate transfer. Keep the tab open during signing. A reload preserves the identity, input snapshot and automatic recovery settings. An interrupted signer is replaced through SDK recovery after reconciliation and the saved retry delay. All status checks retain the five-second countdown.

The selected percentage of the captured sats (rounded down; 50% by default) is the required final Arkade balance. The operator rejects Bitcoin boarding inputs mixed with Bitcoin outputs (INVALID_INTENT_PROOF 23). The spike therefore boards the full captured total, then returns the non-target remainder to the boarding address in a second settlement. Only receipts from the first settlement fund the second; later faucet deposits are untouched. The intermediate whole-total Arkade balance is not success. Automatic boarding starts only for an idle operation with confirmed eligible funding. Currently the exact output checks support the zero fee schedule; a changed/nonzero schedule blocks submission rather than changing the net amount. Dust, expiry and operator limits also block invalid transfers.

Each independently opened window has its own account database, preferences, timing history, and operation locks. Reloading keeps that window's state; opening an already-active window URL in another tab creates a separate state. The first window preserves the previous shared account and history. The identity is encrypted with a browser-local non-extractable AES key in a dedicated IndexedDB database. Step 1 offers explicit Reveal/Hide and Copy controls for recovery details; Step 2 holds the public boarding address. Recovery details are initially hidden, cleared from the page after 60 seconds, on account recreation, or when the tab is hidden, and never logged or placed in timing storage. Do not clear site data while funds or an operation remain.

New accounts store a 12-word BIP39 phrase and restore with `MnemonicIdentity.fromMnemonic(phrase, {isMainnet:false})`. Existing accounts retain their random private key and original address; Step 1 labels them as private-key accounts and identifies `SingleKey.fromHex` as their restore method. A seed phrase cannot be retroactively substituted for these wallets. Recreation does not convert or migrate existing funds. Store recovery details privately and enter them directly in the development app, never in chat or committed configuration.

Success requires both commitments confirmed: the first spends the captured Bitcoin inputs; the second returns exact Bitcoin change and is linked to the exact target in spendable Arkade receipts. Registration alone is pending. Network errors keep the saved operation intact. The isolated automated tests do not establish live funded acceptance.

Interrupted signing is detected with a browser lock held for the settlement session. A restored submitting/registered operation without a live owner becomes uncertain and Step 5 shows **Recovering** for an automatic run, or **Needs attention** when manual intervention is required. Reconciliation continues. Registration errors are persisted before SDK cleanup, with safe network error categories. **Run to completion · including recovery** rechecks the exact captured inputs and amounts before recovering either settlement stage; later deposits are excluded. Automatic onboarding or a recovery click enables recovery for temporary network failures, event-stream failures, and Arkade INTERNAL_ERROR (0). The setting, increasing delay starting at 30 seconds, and attempt count persist across reloads. Transient failures keep retrying, with the delay capped at five minutes. A silent settlement stream is closed after five minutes without events, allowing SDK cleanup to finish before a retry; no second signer is started alongside an abandoned promise. Validation errors stop automatic retries. The SDK's standard duplicate-input cleanup and single re-registration are allowed within each attempt. Cleanup acknowledgement is not completion evidence; only the verified commitments and matching outputs complete the flow. Legacy attempts without saved automatic recovery still require Run to completion once. Validation failures stop automatic signing and require attention. If a boarding acknowledgement was lost, the spike can recover its commitment from a confirmed transaction spending the frozen inputs and an exact linked spendable receipt, then continue the return leg. A lost return acknowledgement is reconciled only when every captured Arkade input has the same settledBy commitment and both confirmed transactions plus the exact Bitcoin change and spendable Arkade receipt match.

## Step timing history

Above Step 1, total duration shows an estimate and the last observed complete run, measured from account restart through Step 6. Completed-run elapsed averages replace the combined step estimates when available, including funding and confirmation waits.

The window-scoped local storage key ending in `standalone-arkade-step-timings-v1` stores per-account step start/end timestamps, completed durations and per-step `{count, totalMs, averageMs}`. Average is total completed milliseconds divided by completed samples. The UI shows this calculation, sample count and current elapsed time. Historical averages replace the rough estimate when available. No wallet secrets or addresses are stored in timing history.

Measurement boundaries: Create/Recreate click to address ready; faucet opened to first deposit detection (a proxy including user/faucet time); first deposit detection to confirmed eligibility; eligibility to automatic onboarding preparation; submission to commitment observed; commitment observed to verified usable funds. Existing steps without recorded starts are not backfilled. Failed or uncertain/in-progress steps do not count as completed samples. Closing the browser does not pause wall-clock timing. Repeated observations, reopening and duplicate clicks do not add samples or reset start times. Recreated accounts contribute independent samples within the same window. Timing-storage failures do not stop wallet processing.

Dependency refresh on 2026-09-09: standalone direct dependencies use SDK 0.4.71, BIP39 2.4.0 and Vite 8.2.2, verified against the npm registry. SDK-pinned transitive cryptography dependencies are retained as published. The live browser footer confirms SDK 0.4.71.

## Live acceptance

### Robustness spike accepted and archived — 2026-09-09

The two reported windows exposed nested operation-lock acquisition during registration/recovery. Checkpoint writes now own a short lock and observations run outside it. The queued-lock regression harness exercises the actual orchestration, including restart while observations hang. Preparation persists the original inputs before SDK work; failed writes cannot publish a submitted state. Provider requests have body-inclusive deadlines and preserve rate-limit cooldowns; timed-out observations cannot accumulate replacement work. Late wallet disposal must finish before another connection starts.

Explicit failed-batch events now recover through the SDK after cleanup and exact-input reconciliation. Validation failures pause. Stale accounts are rejected before intent registration/cleanup, and late acknowledgements cannot overwrite a replacement account. Step-local recovery messages and recheck actions supplement the preserved diagnostic history. A separately verified spendable target is shown while Step 6 waits for the matching Bitcoin confirmation; the final exact-output success predicate is unchanged.

Final automated verification: 89 standalone tests and both standalone/demo production builds pass. The user accepted four funded runs reaching Step 6 and three additional runs also completed. The [robustness change](../../../.openspec/changes/archive/2026-09-09-robust-fixes-for-spike/verification.md) was synced and archived on 2026-09-09 with 11 of 26 tasks complete; 15 broader tasks remain unchecked, including the full fault matrix and timing instrumentation/benchmark. Archival records the accepted spike outcome, not completion of those tasks. New live evidence and limitations are recorded locally under `output/reports/robust-fixes-for-spike/`. Earlier acceptance below predates this robustness pass and is not counted as new acceptance.

The four-run test exposed a batch correlation defect in SDK 0.4.71: it skips a batch start that does not select the current intent, but still throws on that unrelated batch's failure. During recovery, events for the previous intent can arrive on the same input topics and interrupt the new intent before its batch starts. The stream wrapper now matches the registered intent hash to its selected batch and passes through only failures belonging to that batch. It handles the SDK's stream priming before registration, retains actual batch failures, and preserves abort/cleanup behavior. Batch participation acknowledgements have fixed-text diagnostics and an account/intent guard. At 11:52 UTC all four original accounts completed boarding on their first attempt after this fix and automatically entered the return leg; this milestone alone is not Step 6 acceptance.

Final four-run verification at 11:56 UTC: all exact Arkade targets were spendable and both shared commitments confirmed in Signet block 321340. Targets/Bitcoin returns were 24,999/25,000; 24,996/24,996; 24,996/24,997; and 24,611/24,611 sats. Total durations were 33m 21s, 32m 58s, 33m 1s and 33m 3s. Each recorded Step 5 as 26m 58s, including the repeated failures and investigation before the fix; Step 6 took 1m 47s. After the fix, boarding acknowledgement through return finalization took about 62 seconds. These are recovered successes, not four clean runs or a guaranteed future duration.
