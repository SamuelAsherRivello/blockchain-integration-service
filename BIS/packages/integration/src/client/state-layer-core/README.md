# State layer core

This layer owns BIS context lifecycle, immutable public state snapshots, subscriptions, public events, browser-local state records, and cross-layer state reduction. Keep React rendering in `ui-layer-react` and direct Arkade SDK calls in `wallet-layer-arkade`.

Existing context, equipment, continuation, collection and contract controllers remain implementation building blocks and supported non-game consumer exports. Games use facade-owned named `IBis` commands and copied `BisSnapshot`/workflow projections instead of owning those controllers. Financial confirmation and `BisGameEffectReceipt` are separate outcomes: a stale or rejected gameplay effect must not retry payment or minting. Contract recovery owns durable financial progress; the facade forwards its changes through `IBisGame.onBisEvent` without game UI polling.

Read-only wallet projections use the shared bounded retry/cancellation policy. A transient provider, indexer, address, or balance failure may be retried, but only a complete validated read is published as ready; exhausted reads remain unavailable rather than becoming zero or falling back to stale data. Game Wallet observation failures may recover through a fresh read, while wallet selection, logout, network changes, and disposal cancel all pending work.

View snapshots are short-lived and in-memory. The shared cache scopes complete balance, address, asset, contract, activity, and operation-read results by account, network, and data type, with a five-minute default freshness window. Explicit refresh and wallet-operation boundaries bypass or invalidate reuse; account/network lifecycle changes and provider observations invalidate their direct dependents. Consumers must use cached values only for entry rendering and must perform live validation before sending, transferring, swapping, minting, burning, delivering, or otherwise spending.

## Limited-time offers

Loading BIS, recreating a controller, or restoring a durable offer record is passive: it republishes the local contract projection without contacting the provider and without a toast. Provider reconciliation is an intent-bearing action. The Admin Contracts detail view may explicitly check the selected contract; `startContractAsync` starts a new offer; claim, reject, refund, and an active operation may reconcile their own records. A game starts its level-scoped offer at level start, keeps gameplay nonblocking, and queries that exact offer session when the player opens the treasure chest. Durable recovery and reservations remain independent of presentation, so a refresh never creates a duplicate offer or silently spends again. Feedback is shown only for explicit actions or meaningful terminal transitions; an unchanged pending funding record is not a startup notification.
