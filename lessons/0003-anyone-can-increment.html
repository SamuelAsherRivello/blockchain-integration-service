DEMO 01 · SHARED STATE

Anyone can increment

The contract has one integer state value and a one-minute cooldown. There is no owner check: any caller may increment it after the cooldown expires.

contract Counter {
  state counter = 0
  state lastCallAt = null
  const cooldown = 60 seconds

  // No caller restriction: anyone can request this transition.
  function increment(caller, now):
    current = readStateFromInputVtxo()
    require(current.lastCallAt == null OR now >= current.lastCallAt + cooldown)
    next = current.counter + 1

    require(next == current.counter + 1)

    // Preserve the contract's value and replace its state.
    createOutput(
      script = this.script,
      value = input.value,
      state = {
        counter: next,
        lastCallAt: now
      },
      notSpendableBefore = now + cooldown
    )
}

function getCounter(): number:
  vtxo = readCurrentVtxo(counterScript)
  return vtxo.state.counter

// Application flow
counterScript = buildCounterScript(
  initialCounter = 0,
  initialLastCallAt = null,
  cooldown = 60 seconds
)
contractId = wallet.registerContract(counterScript)

// Alice, Bob, or any other wallet can call it.
walletA.call(counterScript, "increment", now)
// Before 60 seconds: rejected.
walletB.call(counterScript, "increment", now + 30 seconds)
// At or after 60 seconds: allowed.
walletB.call(counterScript, "increment", now + 60 seconds)

value = getCounter()

Concurrency rule

Two callers may read the same old VTXO. They cannot both spend the exact same state forever: one transition wins, and the other must refresh the contract state and retry against the new VTXO.

async function incrementWithRetry(wallet, maxAttempts = 3):
  for attempt in 1..maxAttempts:
    try:
      return await wallet.call(counterScript, "increment")
    catch error:
      if error is ConflictingSpend or StaleState:
        await manager.refreshVtxos()
        continue
      throw error
  throw "Could not increment after retrying"

Enforcement note: now is pseudocode. For a rule that must be enforced by Bitcoin rather than merely checked by the application/operator, encode the cooldown as a relative timelock/CSV spending condition. The exact Arkade Script representation depends on the SDK/compiler version.

Arkade interpretation: this is not a shared database integer being mutated in place. Each successful increment consumes one state-bearing VTXO and creates another with the next value.
