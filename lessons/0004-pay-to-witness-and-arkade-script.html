LESSON 04 · BITCOIN CONTRACT FOUNDATIONS

Pay-to-witness: the evidence unlocks the value

The easiest mental model is a locked box. The output contains the lock; the spending input brings evidence that satisfies it.

Lock: “Only a valid signature from this key may spend.”
Witness: “Here is the signature and public key.”
Verifier: “The evidence satisfies the lock, so the spend is valid.”

1. What “pay-to-witness” means

Bitcoin’s Segregated Witness design separates the spending evidence—the witness—from the older transaction data. A pay-to-witness output commits to a witness program. When someone spends it, the input carries a witness stack that must satisfy the committed rule.

This is not a function call returning a result. It is a validity test: either the supplied evidence satisfies the spending condition, or the transaction is invalid.

2. Three useful shapes

P2WPKH: one key

lockingRule = new P2WPKH(playerPubkey)

spendWitness = [playerSignature, playerPubkey]
valid = verify(lockingRule, spendWitness)

Use this mental model for ordinary wallet ownership: the player proves control of the key corresponding to the committed public-key hash.

P2WSH: a script rule

witnessScript =
    require(checkSig(playerSignature, playerPubkey))
    require(checkSequence(oneMinute))

lockingRule = new P2WSH(witnessScript)

spendWitness = [playerSignature, witnessScript]
valid = verify(lockingRule, spendWitness)

The output commits to the script’s hash. The spender reveals the script and supplies the evidence needed to pass it.

P2TR: key path or script path

taprootOutput = new P2TR(internalKey, scriptTree)

// Spend with the key path, or reveal one committed script leaf.
valid = verifyTaprootSpend(taprootOutput, witness)

Taproot lets a contract commit to multiple possible paths while keeping unused paths hidden in ordinary spends. Arkade’s experimental function reference exposes new P2TR, Taproot signature verification, and key-tweaking helpers.

3. The building blocks you will see repeatedly

  • Signatures: prove control of a key with checkSig or checkMultisig.
  • Hashes: commit to a secret before it is revealed, then check it with sha256.
  • Timelocks: delay a path with checkLockTime or relative checkSequence.
  • Require: reject the spend unless a condition is true.
  • Output checks: require the next output to preserve the contract’s value or encode the next state.

4. A game example

A prize could have two paths:

claimPath:
    require(checkSig(winnerSignature, winnerPubkey))

refundPath:
    require(checkSequence(refundDelay))
    require(checkSig(senderSignature, senderPubkey))

The winner’s witness proves the claim path. If the winner never appears, the sender’s witness can use the refund path after the delay. The game server may observe the resulting VTXO event, but it is not the authority that makes the spend valid.
