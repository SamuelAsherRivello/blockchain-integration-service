Where Redis fits

Goal: explain what a backend might put in Redis and what still needs an authoritative source.

Redis is an in-memory data store. It keeps working data in RAM and supports optional disk persistence. A backend can access values by key, such as listing:42. See the official introduction.

A marketplace request

Imagine a React page requesting an item's description through a Node API. The API first checks Redis for a cached copy.

  1. If the copy exists, the API returns it.
  2. Otherwise, the API reads the database, saves a copy in Redis with a 60-second expiration, and returns it.

This is cache-aside. Repeated requests can avoid database reads. The tradeoff is freshness: a cached description can be outdated until it expires or the app invalidates it.

Other backend jobs

  • Sessions share login state across API instances.
  • Rate limits share request counters across API instances.
  • Queues, messaging and leaderboards support background workers, event distribution and rankings.

For your blockchain integration designs, a cached display is a snapshot. A Redis value does not prove a payment or execute an Arkade contract. Verify those operations through the SDK and network.

Recall before revealing

An item sells while its cached listing still says "available." Should the purchase API trust that cached value? Explain your choice.

Reveal feedback

No. The cache may be stale. The purchase flow must check authoritative availability and enforce the purchase rules. For a blockchain operation, it must also validate the relevant network state. Expiration reduces staleness but does not guarantee correctness.
